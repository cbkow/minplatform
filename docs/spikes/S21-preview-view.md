# S21 - the family's presenter and min-ui inside a Quick Look preview's view (opened 2026-11-26)

**Status: VERDICT (macOS 27.2) - PASS (2026-11-26). QCView's presenter draws an EXR into the Quick Look preview's own
view on the extended-range surface, from a sandboxed extension, with a `min-ui` picker over it that the pointer opens
and chooses from. In Finder, on the owner's own files: the first picture 165 ms after the request (bar: 300 ms), a
layer changed in 34 ms. NOT answered: which keys reach the view, and how moving from file to file with Finder's arrows
behaves.**

## Why

Rows 606-607: the preview is the picture with ONE floating bar of QCView's own parts (the layer and the colour as
chips that open `min-ui` popups), an EXR is browsed as a picture with Finder's arrows. S20 showed the system hands us
the request; it drew with AppKit and decoded on the CPU. Unknown: whether the wgpu presenter gets a surface in a view
that Quick Look hosts from another process, whether `min-ui` drawn into it takes the pointer, and how long a file takes
to appear when the person moves from one to the next.

## The question

Does QCView's presenter with a `min-ui` popup draw in the preview's view and take the pointer, and how long from the
request to the first picture?

## Pass bar

A layer of a four-layer EXR chosen from the `min-ui` popup by the pointer, in the system's preview panel; the first
picture within **300 ms** of the request, warm, at 1920 x 1080.

## Time box

Three hours. About an hour and a half used.

## How to run

`zsh packaging/macos/make-app.sh` once (the spike borrows the staged bundle's OpenEXR), then
`zsh spikes/s21-preview-view/build.sh [--adhoc]` builds, signs and registers `target/s21/S21Host.app` with one preview
extension for `com.ilm.openexr-image`: a Swift shell whose view's layer is a `CAMetalLayer`, and this spike's Rust
library (`Presenter`, `UiLayer`, `Picker`, `min_image::exr`) behind six C functions. `--adhoc` signs ad hoc under its
own identifier, so that a shell can read the extension's log at
`~/Library/Containers/app.qcview.spike.s21a.preview/Data/tmp/s21.log`. `--remove` takes it off the system.

## Measurements so far

Apple M5 Max, macOS 27.2.1, the plain sandbox (no exception), `qlmanage -p` held open for a few seconds, a 1920 x 1080
float EXR generated by the vendored ffmpeg, and a four-part one made with `exrmultipart`:

| | very first run | after |
|---|---|---|
| the presenter (instance, surface, device, pipelines) | 1690 ms | 23-25 ms |
| the layer list | 2 ms | 0-3 ms |
| decode + upload | 10 ms | 5-9 ms |
| first picture after the request began | 1843 ms | 165-176 ms |

The surface is Metal, `Rgba16Float` (the extended-range one, as in QCView's own window). The four-part file reports
four layers. The extension is 37 MB (the Rust library unstripped, with its debug information).

## Findings

1. **A `CAMetalLayer` as the view's backing layer, given to wgpu as `SurfaceTargetUnsafe::CoreAnimationLayer`, works in
   the hosted view.** No winit, no window of ours.
2. **The first run on a machine costs 1.7 s** in the presenter (the system's shader cache is empty for a new
   container); every later process start costs about 25 ms.
3. **Of the 170 ms, about 130 are after the upload** - the first `min-ui` layer render and the first present. Not
   taken apart yet.
4. **Rust's temporary folder is not the sandbox's:** `std::env::temp_dir()` named a place the extension may not write;
   `NSTemporaryDirectory()` is the container's `Data/tmp`.
5. **A container made under the Developer ID signature is closed to other programs** (the shell got "Operation not
   permitted" on its log); an ad hoc one is readable. With S20's finding 2: diagnostics of the released extension
   cannot be a file another program reads.

6. **Finder refuses an ad hoc extension that `qlmanage -p` accepts.** From Finder the panel said "Extension
   app.qcview.spike.s21a.preview not found." (after Quick Look's server and cache were reset too); the same spike
   under the Developer ID signature, not notarized, loaded from Finder at once (the owner, on their own EXR: "this
   works"). So a walk build is signed with the Developer ID under a walk identifier, and its readouts are on screen
   (the bar shows the timings and the keys), since its container's log is closed (finding 5).

## The owner's walk (2026-11-26, Finder, the Developer ID build, their own EXR files)

"looks great. Layers work. 165ms first 34ms change": the bar shows, the popup opens and a choice changes the layer;
the bar's own readouts were 165 ms to the first picture and 34 ms for a layer change.

## Not seen

- The keys: which reach the view, which the panel keeps.
- Finder's arrows from one file to the next: whether the process stays, the time per file.
- Finder's preview column, full screen, a second screen, light mode.
- Memory, and what the system allows a preview extension.
- minColor, OCIO, QCView's settings read from inside the sandbox.

## Verdict

PASS. The extension can be built from the family's own presenter and `min-ui`, with no AppKit controls, and it is
fast enough to browse with. The spike dies here: `spikes/s21-preview-view` is not the extension's start.
