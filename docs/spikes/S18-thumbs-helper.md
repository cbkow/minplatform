# S18 - the system's thumbnails and icons from Rust; decoding in helper processes (opened 2026-11-15)

**Status: VERDICT (macOS) - PASS on both halves (2026-11-15). The system's thumbnails and icons arrive as RGBA from a
helper process that has no window, no event loop and no run loop; N helpers behind pipes cost about 1 % of a decode,
scale 3.8x at four, and a file that crashes or hangs one costs exactly its own request. Windows: the code is written
and type-checks for the Windows target; it has NOT been run. Two findings change the design: QuickLook's cancel does
not stop work already started, and `NSWorkspace` registers a helper with the system as an application.**

## Why

The file browser's rebuild (canon rows 455-459) rules: the system's own thumbnails and icons for most file types, our
decoders for production formats, ALL decoding of file contents in helper processes (more copies of the one executable,
as minRender's `--leash`), on-screen work first, unwanted work cancelled. The old application
(`docs/phase5/step0-media-shell-packaging.md`, section 1) blocked a pool worker on a semaphore on macOS and abandoned
a thread at every 10 s timeout on Windows, and one damaged file could take the whole application down.

## The question

(A) Can the system's thumbnails and icons be had from Rust - `QLThumbnailGenerator` and `NSWorkspace` through
`objc2`; `IShellItemImageFactory::GetImage` and the system image list through `windows` - with every wait bounded?

(B) Does the helper-process model work, and what does it cost: N helpers started with `--helper`, a framed protocol
over standard input and output, a scheduler in the parent with priorities and cancellation?

## Pass bar (this Mac, release build)

- A1: thumbnail (where the system has one) and icon as RGBA at 256 and 64 px for a PNG, a JPEG, a PDF, a text file, a
  folder and an application bundle; time per item cold and warm; no thread blocked without a bound or abandoned.
- A2: the calls made inside a helper with no window and no event loop.
- B1: 2,000 JPEGs of 2048 x 2048 to 512 px masters with 1, 2, 4, 8 helpers; the pipe's cost under **10 %** of the
  decode; four helpers at least **3x** one.
- B2: a file that aborts the helper and one that hangs it: a clean failure for that request (hang: within **5 s**), the
  helper replaced within **500 ms**, every other request answered, **20 of 20**; the parent's memory does not grow.
- B3: 5,000 queued, 100 made urgent finish first; cancelling 4,000 costs nothing measurable and frees them.
- B4: a helper's start (spawn to first answer) and its idle memory.

## Time box

Ninety minutes. Kept.

## How to run

`CARGO_TARGET_DIR=target/s18 cargo build --release -p s18-thumbs-helper`, then from the repository's root:
`s18 gen` (2,000 files, 2.1 GiB, under `target/s18-files` - delete the folder afterwards), `s18 sys-thumbs`,
`s18 throughput [n ...]`, `s18 poison [rounds]`, `s18 priority`, `s18 startup`. Each prints its numbers and exits;
no window; no helper is left behind (checked with `pgrep` after every run).

Machine: Apple M5 Max, 18 cores, macOS 27.2. Files generated by the spike; the file cache warm (the numbers are the
decoder's and the pipe's, not the disk's). The decoder is the `image` crate - a stand-in, not the point.

## Measurements

### A1 - the system's thumbnails and icons, as RGBA, made in the helper

Round trip seen by the parent, milliseconds, at 256 px (64 px is the same or less). "Cold": files the system had never
seen (fresh names every run). Pixels are premultiplied RGBA, top row first; the pictures were written out and looked
at (colours, orientation and the PDF's page are right).

| Item | Thumbnail (QuickLook), cold / warm | Size returned | Icon, `NSWorkspace`, cold / warm | Icon, QuickLook, cold / warm |
|---|---|---|---|---|
| PNG 1600 x 1200 | 30 / 1.6 | 256 x 192 | 0.7 - 25 / 0.6 | 0.3 - 10 / 0.14 |
| JPEG 1600 x 1200 | 12 / 1.0 | 256 x 192 | 0.7 - 13 / 0.6 | 0.2 - 8 / 0.14 |
| PDF, one page | 3.3 - 3.8 / 0.9 | 198 x 256 | 0.7 - 13 / 0.6 | 0.2 - 8 / 0.14 |
| Text file | 11 - 14 / 1.3 | 256 x 256 | 0.7 - 20 / 0.5 | 0.2 - 10 / 0.14 |
| Folder | none, said in 1.5 - 2.0 | - | 0.6 - 20 / 0.5 | 0.5 - 18 / 0.3 |
| Application bundle | none, said in 4 - 7 | - | 7 - 68 / 5.8 | 1.8 - 11 / 1.7 |
| Icon of a TYPE (extension alone, no file) | - | 256 x 256 | 0.1 - 17 / 0.05 - 0.5 | - |

The ranges in the icon columns are the same call on two runs: the high figure is the very first use of a type's icon
after a long time (the first `NSWorkspace` call of a helper also loads AppKit: 25 ms), the low one is what the second
run saw for brand-new files, because the system keeps icons per type. A thumbnail's cold cost is real work every time.

- A folder and an application have no thumbnail (QuickLook answers with an error in a few ms): the icon is their
  picture. QuickLook's own "icon" representation gives the same icon as `NSWorkspace` (an application's own, a
  folder's), asynchronously, and was never slower.
- Helper memory after 112 system requests: 8.5 - 13 MiB footprint (37 - 43 MiB resident, mostly shared frameworks).

**Bounding and cancelling.** The thumbnail request is asynchronous: the helper's thread waits for the answer on a
channel with a time limit - never on a semaphore without one. Tried on a 9000 x 9000 PNG the system takes 0.62 s for:

| | Result |
|---|---|
| Soft bound 50 ms, then `cancelRequest:` | the system did NOT call the handler within 100 ms more: **the cancel does not stop a generation already running** (with a 2 s wait the handler came 568 ms later, i.e. when the work ended) |
| What the helper does then | stops waiting and answers "timeout" at 156 ms; the late answer is dropped (its channel is closed). The work was never on a thread of ours - it runs in the system's agent |
| The next request on the same helper | 1.2 - 2.2 ms; the helper was never replaced |
| The cancelled file asked again at once | 1.06 - 1.23 s instead of 0.62: it waits behind the generation still running |
| A request that never answers at all | the parent's hard bound: the helper process is killed and replaced (B2) |

### A2 - what the calls need

Nothing: no run loop, no `NSApplication`, no window. QuickLook's handler arrives on a queue of its own while the
helper's main thread waits on a channel. But the two APIs differ in what they do to the process:

| Helper does | Launch Services sees the helper as (`lsappinfo`) |
|---|---|
| QuickLook thumbnail or QuickLook icon; a bare executable or one inside an `.app` | not registered at all |
| `NSWorkspace` icon (of a file or of a type), bare executable | registered, "BackgroundOnly" |
| `NSWorkspace` icon, the executable inside an `.app` bundle | registered under the bundle's name as **"Foreground"** |
| The same, after `NSApplication.setActivationPolicy(Prohibited)` at the helper's start | "BackgroundOnly" |

A helper that is the application's own executable and calls `NSWorkspace` is, to the system, a second foreground
copy of the application. Whether that shows in the Dock was not looked at (the spike does not look at the desktop);
the design below does not depend on the answer.

Pipe cost = the parent's round trip (first byte of the request written to last byte of the answer read) minus the
helper's own decode and encode time. An RGBA master is copied twice (helper to kernel, kernel to parent), 1 MiB each.

- Helpers are as fast as threads in one process, and faster at eight (each has its own allocator).
- Sending RGBA costs 0.2 - 0.3 ms; encoding a JPEG in the helper to save that costs 1.6 - 1.8 ms (and the parent must
  decode it again). **RGBA over the pipe wins**; a JPEG is worth making only if it is what goes to a disk cache.

### B2 - crash isolation (4 helpers; 20 rounds of 40 good files + one that calls `abort()` + one that loops for ever)

| | Result |
|---|---|
| Rounds passed | **20 of 20** |
| Good files answered correctly, every round | 40 of 40 |
| The aborting file: "crashed" reported for that request after | mean 0.8 ms, max 0.9 ms |
| The hanging file: "hung" reported after (bound 5,000 ms; the watchdog kills the helper) | mean 5,006 ms, max 5,011 ms |
| A dead helper replaced (the old one reaped, the new one's hello read) | mean 3.9 ms, max 5.6 ms, 40 replacements |
| Parent memory, before / after | footprint 5.3 / 5.5 MiB, resident 11.8 / 14.0 MiB |
| Helpers alive at the end | 4; none left after exit |

With the helper's crash handler off (the system's default), the crash was seen just as fast (0.2 ms) - but macOS
wrote a crash report into the user's diagnostic reports for every damaged file (3 for 3; removed). With the handler
(the signal ends the process at once) nothing is written.

### B3 - priority and cancellation (4 helpers)

| | Result |
|---|---|
| 5,000 requests queued | 0.11 ms; parent footprint 11.5 -> 11.8 MiB |
| 100 at the END of the queue marked urgent | 7 microseconds |
| First urgent answer / all 100 | 28.5 ms / 824 ms |
| Non-urgent answers in between | 4 - exactly the four already in flight. PASS |
| Cancelling 4,000 queued | 213 microseconds (53 ns each); queued 4,865 -> 865; ids held 4,965 -> 865; footprint unchanged at this resolution (a queued request is about 100 bytes) |
| Answers for cancelled requests / anything after the last answer | 0 / nothing. PASS |

A request in flight is not interrupted by an urgent one (it is at most one decode away, 25 ms); a cancelled request
in flight is left to finish and its answer dropped.

The spike's executable is small. The product's helper is the application's executable: its start must be measured
again with everything the application links, and `main` must branch to the helper before anything else is set up.

## The protocol, and whether pipes are enough

Frames on the helper's standard input and output: a u32 length, then
`request = id u64 | op u8 | format u8 | size u16 | soft bound ms u32 | path` and
`response = id u64 | status u8 | width u16 | height u16 | work us u32 | aux u32 | payload`. The helper says hello
with one empty response at its start. One request is in flight per helper, so a death or a hang always belongs to
exactly one request. The parent refuses an answer over 64 MiB.

**Pipes are enough; shared memory is not needed.** A 1 MiB master crosses in 0.2 - 0.3 ms, 1 % of its decode. Even a
2048 px master (16 MiB, some 4 ms by the same rate - not measured) is small beside the decode that made it. Windows
pipes have a smaller default buffer; the same figure must be taken there before this is final.

## How many helpers, and when [proposed]

- None at launch. The first request starts one (3 - 6 ms); more are started as the queue grows, up to
  **half the machine's cores, at least 2, at most 8** for our own decoders (3.8x at four, 7x at eight here).
- **One more helper for the system's thumbnails and icons**, apart from the decoders: those requests mostly wait on
  the system's agent, and a plug-in that hangs must not hold a decoder.
- A helper idle for about 30 s is ended: it is 2 MiB fresh but 21 - 25 MiB after work, and a new one costs 3 ms.

## What the real implementation must own

1. The helper mode as the first branch of `main`; stdin's end is the order to leave; a busy helper also watches for
   its parent's death (Unix: the parent's id changes; Windows: a job that dies with the application).
2. The scheduler: urgent and normal queues, promotion, cancellation that frees a queued request at once, one request
   in flight per helper, results taken through a BOUNDED channel (in the spike, results waiting to be read were the
   parent's only memory growth: 1 MiB each).
3. One watchdog thread: a hard bound per kind of request (5 s was used), the helper killed at it, replaced, the
   failure reported BEFORE the replacement starts. Also a bound on a helper's start (the spike has none).
4. "Cannot preview" remembered per file (identity + modification time), so that a damaged file is not tried again at
   every scroll, and does not kill a helper each time.
5. A crash handler in the helper that ends the process at once (no crash report per damaged file) - or the decision
   to keep those reports.
6. macOS: thumbnails AND per-file icons through QuickLook (asynchronous, bounded, no registration with the system);
   a soft bound, `cancelRequest:`, then stop waiting - the cancel is a hint, not a stop. Icons per TYPE read no file
   contents: make them in the application itself, or in a helper that first sets its policy to "Prohibited".
   Pixels are premultiplied; the spike drew in device RGB - the product names sRGB.
7. Windows (unrun): `GetImage` is synchronous and cannot be cancelled - its only bound is the watchdog killing the
   helper, which is exactly what replaces the old application's abandoned threads; COM initialised once per helper,
   apartment-threaded, on the thread that calls; no console window; error boxes off.

## Windows - written, not run

`src/sys_win.rs` (`IShellItemImageFactory::GetImage` with `SIIGBF_THUMBNAILONLY` / `SIIGBF_ICONONLY`, the bitmap read
with `GetDIBits` as premultiplied BGRA and swapped; type icons through `SHGetFileInfoW` with
`SHGFI_SYSICONINDEX | SHGFI_USEFILEATTRIBUTES` and `SHGetImageList`), the job object in `src/pool.rs` and the memory
reading in `src/main.rs` compile for `x86_64-pc-windows-msvc` (`cargo check`). Nothing of it has been executed. To
see there: every table above; the pipe's cost with Windows' buffer; whether a 32-bit bitmap from an old handler has
alpha; the helper inside a Store package.

## Verdict

**macOS - (A) PASS:** thumbnails and icons as RGBA at 256 and 64 px for every item, from a helper with no window and
no loop; every wait bounded, nothing abandoned. **(B) PASS:** pipe cost 0.95 % of the decode (bar: under 10 %);
four helpers 3.76x one (bar: 3x); 20 of 20 poison rounds, failure in under 1 ms (crash) and at 5.0 s (hang),
replacement in under 6 ms (bar: 500 ms); urgent first, cancel free; a helper starts in 3 - 6 ms and idles at 2 MiB.

**Windows: not run.**

**Open:** the Windows run; whether a "Foreground" registration shows in the Dock (avoided by the design in point 6);
the product's own executable's start time as a helper; pipe cost for masters larger than 512 px.

## Windows, run 2026-11-15 (Windows 11, the same commands, in the desktop session)

Two faults of the Windows code as first written, both the same answer from the shell (`E_INVALIDARG`, 0x80070057) and
both mended: the shell's parser takes only an ABSOLUTE path with backslashes, and NOT the `\\?\` form that
`std::fs::canonicalize` returns. The real application needs one function for "a path as the shell takes it".
