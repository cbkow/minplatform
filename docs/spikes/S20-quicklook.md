# S20 - a Quick Look extension for the files macOS shows nothing for (opened 2026-11-26)

**Status: VERDICT (macOS 27.2) - PASS (2026-11-26). The system hands a QCView-signed extension the thumbnail and the
preview requests for MXF, DPX, MKV and EXR - EXR too, although the system has a picture of its own for it. With one
sandbox exception the extension lists the file's folder and reads its neighbours. A real decode through the family's
FFmpeg, inside the sandbox and under the hardened runtime, answers in 18-57 ms warm at 1920 x 1080 (bar: 300 ms). NOT
seen: the pointer and the keys inside the preview's view (the owner's walk), notarization of the exception, a clean
machine.**

## Why

The owner (2026-11-26) asked for a Quick Look extension for the media QCView reads and macOS does not: MXF, EXR,
sequences. Before a design, three things were unknown: whether macOS lets a third party take a type it declares itself
(reports on Apple's forums say an extension naming `public.jpeg-2000` was refused at validation); whether a sandboxed
extension, handed one file, can read the other frames of a sequence; whether our decoder runs in such a process. The
owner pointed at Tristimulator (github.com/alexfry/Tristimulator, MIT), whose view-based preview extension names
`com.ilm.openexr-image` and draws through Metal.

## The question

Does macOS 27 give a QCView extension the thumbnail and the preview requests for MXF, DPX, MKV and EXR, and can it
read a frame's neighbours?

## Pass bar

From a signed bundle, the system's thumbnail (asked as Finder asks: `QLThumbnailGenerator`) is OURS for MXF, DPX and
MKV, each within **300 ms** warm at 1920 x 1080.

## Time box

Two hours. Kept (about ninety minutes).

## How to run

`zsh packaging/macos/make-app.sh` once (the spike borrows the staged bundle's FFmpeg libraries), then from the root:
`zsh spikes/s20-quicklook/build.sh [--siblings] [--identity "<Developer ID Application: ...>"]` builds
`target/s20/S20Host.app` with `S20Thumb.appex` and `S20Preview.appex` by hand (swiftc, no Xcode project), signs and
registers it. `target/s20/probe <out dir> <files...>` asks the system for each file's thumbnail, times it and writes
it as a PNG. The placard run (whose thumbnail is it) was the first build, before the decode was linked in. **`zsh spikes/s20-quicklook/build.sh --remove` takes it off the system again**
(the registration, the bundle, Quick Look's cache).

Machine: Apple M5 Max, macOS 27.2.1. Files generated by the vendored ffmpeg from `testsrc2` (ProRes, DNxHR and MPEG-2
in MXF, ProRes in MKV, 10-bit DPX, float zip EXR).

## Measurements

**Before, nothing registered** (`qlmanage -t`, 20 s bound): a thumbnail for EXR and TGA; none for MXF (all three),
DPX, MKV. The types: `org.smpte.mxf` and `com.ilm.openexr-image` are the system's; `.dpx` and `.mkv` had only dynamic
types until the host bundle declared `org.smpte.dpx` and `org.matroska.mkv` as imported types (the identifiers are the
spike's choice, not a ruling).

**Whose thumbnail (placard build, ad hoc signature):** ours for EXR, DPX, MXF (both), MKV; the system's for the
controls (a ProRes MOV, a TGA). 6-15 ms each, the first call 235-284 ms (the process starts).

**Whose preview** (`qlmanage -p`, five seconds each, a line left in the extension's container): ours for EXR, MXF,
DPX, MKV.

**Neighbours:** with the plain sandbox (`app-sandbox`, `files.user-selected.read-only`) the folder is not readable.
With `com.apple.security.temporary-exception.files.absolute-path.read-only` = `/` added, both extensions listed the
folder (9 entries) and read 16 bytes of a neighbour. Narrower forms of the exception were not tried.

**The decode** (Developer ID signature, hardened runtime, sandbox with the exception; a Rust static library on raw
FFmpeg linked into the Swift extension, the FFmpeg libraries in the HOST's `Contents/Frameworks`, found through
`@loader_path/../../../../Frameworks`; 256 px asked, round trip seen by the probe):

| File, 1920 x 1080 | first | second | third |
|---|---|---|---|
| DNxHR HQ in MXF | 392 ms (process start) | 57 ms | 37 ms |
| MPEG-2 422 in MXF | 18 ms | 18 ms | 18 ms |
| ProRes HQ in MXF | 54 ms | 45 ms | 36 ms |
| ProRes in MKV | 49 ms | 49 ms | 44 ms |
| DPX, 10 bit | 40 ms | 33 ms | 40 ms |
| EXR, float zip | 92 ms | 92 ms | 105 ms |

The picture was written out and looked at (the ProRes MXF: the test pattern, right way up).

## Findings that change the design

1. **A type the system declares can be taken, EXR included,** for the thumbnail and for the preview, on macOS 27.2. No
   validation step ran here (nothing was notarized or sent to a store), so the forum report is not contradicted for
   the App Store.
2. **A container belongs to the signature that made it.** The same extension identifier signed first ad hoc and then
   with the Developer ID never answered: the process waited for ever in the sandbox's start (`_libsecinit_appsandbox`)
   and the system's thumbnail call failed after 60 s. A fresh identifier answered at once. For the release this means:
   one identifier, always the release signature; walk builds get their own identifier.
3. **The extension was used straight after registration,** without being switched on in System Settings, on this Mac.
4. **A Swift shell around a Rust library works** and is small (the shell is about fifty lines per extension). An
   extension written wholly in Rust was not tried.
5. The unified log gave none of the extensions' lines back (`log show`), and the thumbnail extension left no file in
   its container although the preview extension did. Plan the release's diagnostics on something else.

## Later the same day: the EXR THUMBNAIL is not ours any more (unexplained)

When the real thumbnail extension was built (canon row 612), the system's thumbnail of an EXR came from the system's
own generator again, and no extension's process was started for the request - not the walk build's, and not this
spike's either when it was registered again, ad hoc and under the Developer ID, alone and beside the walk build, after
`qlmanage -r`, `qlmanage -r cache` and a restart of the thumbnails agent. An MXF's request reached each of them every
time. The morning's placard run above (EXR "OURS", the magenta picture looked at) was real; what changed between is
not known. Finding 1 therefore stands for the PREVIEW (walked by the owner all day) and for MXF, DPX and MKV
thumbnails; **for the EXR thumbnail it was seen once and could not be had again.** Tried after that, no change: the EXR type declared as imported, with a document type, in the host's Info.plist (as
Tristimulator's host has it). Not tried: after a restart of the Mac, another machine, a notarized bundle.

## Not seen

- The pointer and the keys inside our view (the preview has a slider, a button and a key readout for this): a person's
  walk, space bar in Finder.
- Finder itself drawing the thumbnails, and what it does with pictures it cached before.
- Notarization of an extension carrying the exception, and Gatekeeper on another machine.
- An update replacing the bundle (Sparkle) and the system noticing the new extension.
- Colour: the spike's pictures are FFmpeg's plain conversion - an EXR is shown linear, WORSE than the system's own.
- Extended range in the preview's view (Tristimulator does it with a Metal layer on macOS 26.4 and later).
- A sequence played or even named: only "a neighbour can be read".

## Verdict

PASS. The extension is possible for every type asked, EXR included, with our own decoder and with sequences in reach.
The spike dies here: `spikes/s20-quicklook` is not the extension's start.
