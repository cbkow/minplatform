## Proposed, awaiting the user
- **The shape of the text shown to the desktop** — OPEN, and the first thing to settle next session. Three shapes: one
  field per paragraph (tested: fast, but Grammarly checks only the paragraph the caret is in — the user felt that at
  once and asked whether the block model itself should be reassessed); one field per run of text between media /
  table / column blocks (untested); the whole note as one field (correct; slow to catch up after a scroll on a
  50,000-word worst case, never tried on a realistic text). The block model is NOT in question: how the document is
  built and how its text is described to the desktop are independent, and the user accepted that ("that is a good
  point").
- The paste ladder's order kept; RTF not read from the clipboard; web images downloaded into the note; our own paginated
  PDF (QCView 3's krilla route).
- A whole Obsidian vault vs. single files; several collections and recents; one media folder beside the collection.

## The spike S9, where it stands (macOS only; Grammarly Desktop 1.207.0)
- Grammarly attaches to an unknown, custom-drawn view at once. It needs: value, selectedTextRange (get / set),
  selectedText, frameForRange, frame — nothing else was called. It applies a correction by setting the selection,
  reading it back, then TYPING the replacement as key events of up to 16 UTF-16 units.
- The hand-written reference window (`tools/s9/`, flat text, TextKit geometry) was right the first time and stays fast
  at 50,000 words. The AccessKit route (`spikes/s3-text`) works after four fixes of ours but is O(document) per update
  and per query: too slow on long text.
- Grammarly re-asks the geometry of EVERY flagged range after every scroll; at 50,000 hostile words that is seconds of
  catch-up. Field size is the only lever.
- LEANING, not a verdict: the editor's text element is written directly against the platform's text protocol over a
  flat text + block map; AccessKit serves the rest of the interface.

**FIRST next session (needs the user for one minute):** the whole-note shape on the realistic 5,000-word text — the

**Then, in the spike (none needs the user):** (1) the hand-written text element INSIDE the real stack — today it exists

## How to run the spike's pieces
- `sh tools/s9/build.sh` → `target/spikes/s9/S9Text.app`; `open -n <app> --env S9_LOG=<file> [--env S9_FILE=<text>]
  [--env S9_OFF=a,b] [--env S9_OFFSCREEN=zero]`. Launch with `open`, not the bare binary: the tool keys on the bundle.
- The stack: `cargo build --release -p s3-text`, copy the binary into an `.app` (see the spike log), `--file <text>`,
  `S9_ALL_LINES=1` to expose every line.
- `swift tools/s9/axcheck.swift <pid> [step]` — the outside check (reads + selection round trips; it types nothing).
- Logs and generated texts: `docs/spikes/s9/out/` (ignored).
- Never inject keys into the user's desktop; the user accepts suggestions by hand and the log is read afterwards.

## Addendum 2, 2026-11-11 (end of session) — where the spike S9 stands
Read the spike log's steps 3d–3f and 4 (`docs/spikes/S9-desktop-text.md`); the verdict is still PENDING.

- **Done — step 3f: the hand-written element works inside the real stack** (`spikes/s3-text`, `S9_NATIVE=1`,
  `src/native_ax.rs`). One more dynamic subclass, layered on AccessKit's subclass of winit's view, adds our
  `NSAccessibilityElement` to the children and answers focus and hit-test; nothing is patched. The user accepted
  Grammarly's corrections in that window by hand and every one landed on the intended text.
- **What the element had to be** for Grammarly to attach and keep up: (a) the WHOLE text protocol declared (line and
  range queries, the attributed string, both setters) — with only the calls Grammarly really makes, it never read the
  value; (b) flat UTF-16 text; (c) the frame of the whole document, moving with the scroll, no layout notification;
  (d) the text inside an `AXScrollArea` element with an `AXScrollBar` that posts `AXValueChanged` on scroll
  (`S9_SCROLLNOTE=area`) — without it the user saw the lag again although the log showed timely answers.
- **Done — step 4: `NSSpellChecker` called directly** (`tools/s9/spellcheck.swift`): spelling and a thin grammar
  layer, about 1 ms per paragraph. Traps: grammar returns nothing unless asked together with spelling, and an
  orthography option silences it.
- **Open, needs the user's machine left alone for a minute** (the tests need the window frontmost, about 13 s each):
  which of the seven added methods Grammarly requires (`S9_OMIT=<selector,…>`); whether the scroll area also helps
  when the view scrolls WITHOUT wheel events (`S9_AUTOSCROLL=1` — without the scroll area Grammarly caught up about
  2.5 s late; keyboard paging, a dragged bar and jumps are this case); the `layout` variant was never measured in
  the stack.
- **Open, needs the user:** the 50,000-word text in the working window (the "enormous" threshold of row 276);
  Grammarly on the Windows box before the Windows leg (their call).
- **Open, needs nobody:** Writing Tools' limited mode; undo coalescing of Grammarly's typed bursts re-tested in the
  stack; the VoiceOver item of the pass bar; key-to-picture p95 at 50,000 words with Grammarly attached; why the
  scroll area matters; then the written verdict.
- **Known wrinkles:** the log's step 3e says Grammarly reads the frame "once per scroll event" — those counts are
  de-duplicated log lines (frame CHANGES seen), not calls; "the window shows no text until focused" got a
  `request_redraw()` in `init`, not confirmed by the user.
- **To launch the working window:** `cargo build --release -p s3-text`, copy the binary into an `.app` bundle with its
  own bundle id, then `open -n <app> --env S9_NATIVE=1 --env S9_SCROLLNOTE=area --env S9_LOG=<log> --args --file
  <text> [--seconds N]`. Keep the text and the log outside `~/Documents` (a temporary folder): a re-signed bundle
  reading under Documents hangs on the permission dialog.
- Row 275 (one undo history, one shortcut table) is still PROPOSED, as are the paste ladder, vault import and recents.

## Addendum 3, 2026-11-11 (after the QCView 3.0.2 release) — the two hands-off tests are done
Spike log, step 3g. **`setAccessibilityValue:` alone is what makes Grammarly treat the element as text**: leave it off
and it never reads the value; keep it and drop the other six added methods and it attaches at once. **With the scroll
area, a view that scrolls itself is followed** (about 13 frame reads a second; none with no announcement), so keyboard
paging and a dragged bar are served by the same tree. Both items leave "Open" in Addendum 2.
Still open: for the user — the 50,000-word text in the working window; Grammarly on the Windows box. For nobody —
Writing Tools' limited mode, undo coalescing in the stack, the VoiceOver item, key-to-picture p95 at 50,000 words with
Grammarly attached, why the scroll area matters to the eye; then the verdict.
To repeat a run: the bundle `target/spikes/s9/S9Native2.app` (not rebuilt since 07:08), the text and the log in a
temporary folder, `open -W -n <app> --env S9_NATIVE=1 --env S9_SCROLLNOTE=area --env S9_LOG=<log> [--env S9_OMIT=<a,b>]
[--env S9_AUTOSCROLL=1] --args --file <text> --seconds 12`.
